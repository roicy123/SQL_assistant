# Sales Data Assistant (Text-to-SQL)

A natural-language interface to a SQLite sales database. The user asks a question in plain English, an LLM writes a SQL query, the query is validated and run on a **read-only** connection, and the result is shown as a table with a one-line summary. The generated SQL is always visible.

> The database is synthetic (generated by `app/make_db.py`): 40 customers, 12 products, 320 orders, 796 order items.

## Features

- **Natural language to SQL** with the schema and rules passed to the model.
- **Two independent safety layers:** a SELECT-only validator (one statement, no write keywords) and a read-only database connection enforced by SQLite itself.
- **One retry on SQL errors:** the database error is sent back to the model once. Guard rejections are never retried.
- **Transparent answers:** the UI shows the summary, the result table, the generated SQL, and the number of attempts.
- **Execution-accuracy evaluation** that compares result sets against hand-written gold queries, plus attack tests for the guard.

## Architecture

```
question + DB schema ──► LLM writes SQL ──► validator (one SELECT/WITH, no write keywords)
      ──► READ-ONLY SQLite connection ──► rows ──► LLM one-line summary ──► answer + table + SQL
                 └─ SQLite error?  send the error back to the LLM, retry once
                 └─ validator rejection?  stop (never retried)
                 └─ off-topic or write request?  the model answers CANNOT_ANSWER and nothing runs
```

The validator is a blocklist, so it can have false positives and could be bypassed in principle. The read-only connection is the real protection, because it is enforced by the database engine. Using both means neither has to be perfect.

## Run it

```powershell
python -m venv env
env\Scripts\Activate.ps1            # macOS/Linux: source env/bin/activate
pip install -r requirements.txt
copy .env.example .env              # macOS/Linux: cp .env.example .env, then add your GROQ_API_KEY
python -m app.make_db               # creates sales.db
python -m pytest -q tests           # 12 guard tests
uvicorn app.main:app --reload       # terminal 1
streamlit run ui/streamlit_app.py   # terminal 2
python -m eval.evaluate             # evaluation (about 60 LLM calls)
```

Groq retires models from time to time. If you get a `model_not_found` error, update `GROQ_MODEL` in `.env`.

## Evaluation

`python -m eval.evaluate` runs 25 questions (8 easy, 10 medium, 7 hard) against hand-written gold SQL. A question counts as correct when the model's **result set** matches the gold result set (row order is ignored, floats are rounded to 2 decimals, column names are ignored). Comparing results instead of SQL text means different but equivalent queries are accepted.

Two scoring rules are reported:

- **Strict:** the same rows and the same number of columns.
- **Relaxed:** also correct if some choice of the model's columns reproduces the gold result, so extra columns (for example an ID next to a name) are allowed. **I defined this rule after reviewing the strict failures**, so it is reported next to the strict score and not instead of it.

Two prompt variants were compared: schema and rules only, and schema and rules plus 3 example queries (none of which appear in the question set). The whole evaluation was run twice, with no changes between runs.

| Variant | Run 1 strict | Run 2 strict | Run 1 relaxed | Run 2 relaxed |
|---|---|---|---|---|
| Schema only | 21/25 | 21/25 | 25/25 | 25/25 |
| Schema + 3 examples | 23/25 | 23/25 | 25/25 | 25/25 |

By difficulty (same in both runs): easy 8/8, medium 10/10, and hard 3/7 (schema only) or 5/7 (with examples) under strict scoring; hard is 7/7 for both under relaxed scoring.

### Failure analysis

All 6 strict failures (in each run) returned **exactly the right rows plus an extra column**, usually a `customer_id` or `product_id` next to a name. I confirmed this by running each failing query and comparing it to the gold result. No query returned a wrong result. The failing questions were the same in both runs (`h1`, `h3`, `h5`, `h7` for schema only; `h1`, `h3` with examples), although the generated SQL text differed between runs even at temperature 0 (for example `NOT EXISTS` versus `LEFT JOIN ... IS NULL` for the same question).

### What I found

1. **The few-shot examples did not improve correctness.** The strict difference (21 vs 23) comes entirely from two questions where the schema-only prompt happened to add an ID column. Under relaxed scoring both variants are 25/25. The examples changed how often extra columns appeared, which is a formatting effect, not an accuracy gain.
2. **Prompt-level attacks never reached the guard.** All 6 injection prompts (delete rows, drop a table, a piggy-backed `DROP`, update prices, `PRAGMA`, insert a row) were refused by the model itself (`CANNOT_ANSWER`), so 0 were blocked by the validator, and the database was unchanged. To test the guard on its own, 7 malicious SQL strings were sent straight to it with the model bypassed: **7/7 blocked**, database unchanged. The guard is also covered by 12 unit tests, including one that shows the read-only connection rejects a write even when the validator is skipped.
3. **A manual check found a bug the evaluation can't see.** The first summary of the top-customers question showed amounts with a `$` sign, because the model guessed a currency. The evaluation compares result sets and does not score summaries. I fixed it by stating in the summarizer prompt that amounts are in Indian rupees.

## Limitations

- Synthetic data in a single SQLite database. A production database would add dialect differences, much larger tables, and permissions.
- The 25 questions and their gold queries were written by the same person, and the wording is specific (for example "completed orders"). Ambiguous questions ("best customers", "recent orders") were not tested.
- Both prompt variants reach 25/25 under relaxed scoring, so this question set cannot tell them apart. A harder set would be needed to compare prompts.
- The relaxed rule was defined after seeing the failures. Strict scores are reported alongside it.
- Result-set comparison could pass an answer by coincidence, and summaries are not scored.
- Only 6 prompt-level attacks, all non-adaptive. They show the model refuses obvious requests, not that it cannot be talked into writing a write query.
- The keyword blocklist is blunt: it would also reject a harmless query that mentions a column named, for example, `replace_date`.
- No query timeout and no table-level permissions. Results are capped at 200 rows. There is no authentication.
- Results come from one model (`openai/gpt-oss-120b`) and two runs. Generated SQL varies between runs.
